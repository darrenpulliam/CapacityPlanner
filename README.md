# Capacity Planner

Standalone project, separate from CrystalBull. Garmin → capacity tier → calendar.

**Flow:** Garmin watch → Garmin Connect → `garmin_capacity.py` (Task Scheduler `\Capacity\Capacity_Morning` 09:00, `Capacity_Retry` 10:15; retimed 2026-10-16 from 07:25/08:40) → Telegram card + `[CAPACITY]` mail → cloud Claude task "Capacity calendar writer" (08:52 ET) → Google Calendar (dppharmd@gmail.com).

**On demand (`--now`, 2026-10-17):** current readings through the day: latest Body Battery with its time, today's high/low, latest stress, latest HR, today's RHR, last watch sync (flagged STALE after 60 min) and this morning's tier for reference. Telegram line `NOW <time>: BB <n> (high/low), stress <n>, HR <n>, synced <time>` plus a `[CAPACITY-NOW] <date> <time> BB<n>` mail with a `<<<CAPACITY_NOW_JSON` block. Always calls Garmin; never touches the morning files (writes `data\now\` and `data\now_latest.json`). Run it with `Start-ScheduledTask -TaskPath '\Capacity\' -TaskName Capacity_Now` (no trigger, S4U, logs to `data\task.log`) or `/capacity` on the planner's own bot.

**Telegram bot (2026-10-18): `@dp_health_consultant_bot` ("Health Consultant"), `capacity_bot.py`.** Moved off `@crystalbull_ai_bot`; the morning card, the retry and `--now` all post through this bot's token. Long-polls `getUpdates` with stdlib urllib (plain `requests` black-holes on this PC, see `b20bfce`). Owner chat only (`TELEGRAM_CHAT_ID`). Commands, registered with `setMyCommands`: `/capacity` (runs `--now`, which posts the NOW card), `/today` (reposts this morning's card from `data\latest.json`), `/help`; anything else gets a one-line hint. Single instance via `data\capacity_bot.lock`; heartbeat `data\bot_heartbeat`; update offset in `data\capacity_bot_state.json`; commands queued more than 10 min while it was down are skipped with a note. Task `\Capacity\Capacity_Bot`: at logon + at startup, S4U, restart every 1 min on failure (999), no time limit, logs to `data\task.log`. It is the one poller on its token.

| Tier | Body Battery at wake | Deep-work blocks | Bedtime shift |
|---|---|---|---|
| GREEN | ≥ 50 | 3 | 0 |
| YELLOW | 25–49 | 2 | −15 min |
| RED | < 25 | 1 | −30 min |

- Drops one tier if sleep score < 60 or HRV status is UNBALANCED/LOW.
- Sleep debt (an average of under 7h15m over at least 2 nights) moves bedtime another 15 min earlier. Bedtime never moves more than 45 min earlier.
- Wake is fixed at **8:30 AM** (shift-work anchor). Sleep need is 8h plus 15 min to fall asleep, so standard bedtime is **12:15 AM**, wind-down starts at 11:15 PM and caffeine cutoff is 3:15 PM. Tier cutoffs were recalibrated on 2026-10-07 from 12 months of Garmin history (median Body Battery at wake about 35). Change these with the constants at the top of `garmin_capacity.py`.

**Extra sources (2026-10-23, `sources_extra.py`):** ResMed myAir (CPAP) and Sleep Number SleepIQ, both best-effort (a failure logs a WARNING in `data\task.log` and the run continues with Garmin only). One-time setup: `python garmin_capacity.py --setup-myair` (e-mail/password, then the e-mailed MFA code; tokens + Okta remembered-device cookie in `%USERPROFILE%\.myair\tokens.json`) and `--setup-sleepiq` (e-mail/password; asks which sleeper if the bed has two; choice in `%USERPROFILE%\.sleepiq\session.json`). Both write `MYAIR_*` / `SLEEPIQ_*` to `.env` without echoing them. Scheduled runs never prompt: myAir reuses the access token while Okta says it is active, then signs in again with the remembered device (no MFA); if Okta still wants a code the source is skipped. Rules: `sleep_min` falls back Garmin -> SleepIQ (in bed - restless - out of bed) -> CPAP usage (`metrics.sleep_source`); SleepIQ score < 60 only counts when Garmin has no sleep score; AHI >= 5 joins the one-tier downgrade (still max one); AHI >= 15 adds "check mask/pressure"; CPAP < 240 min sets the sleep-debt flag (-15 min, -45 cap); high leak (> 24 L/min 95th pct) or mask seal score < 15 (`cpap.mask_seal_score`, 0-20; `cpap.mask_onoff_score` 0-5 and `cpap.mask_pairs` are informational) adds "mask seal". Watch not worn (no Garmin sleep record AND `bb_charged_overnight` = 0): Body Battery at wake is stale, so the base tier comes from the SleepIQ score (>= 80 GREEN, 60-79 YELLOW, < 60 RED) and the one-tier downgrade OR still applies; `metrics.tier_source` is `garmin` or `sleepiq`; without SleepIQ the Body Battery tier is used as before. The bed-entry-vs-target comparison is done by the cloud calendar writer (shift-aware), not here. Payload / mail JSON gain `cpap` and `sleepnumber` objects (null when missing); subject and `<<<CAPACITY_JSON` markers unchanged. `--no-extra` skips both. `--mock <scenario>` exercises one rule each (see `MOCK_CASES`).

**Weather / barometric pain (2026-10-23, `sources_extra.fetch_weather`):** Open-Meteo hourly sea-level pressure (free, no key) for the configured location. Set `WEATHER_PLACE` (e.g. `Frankfort, KY`; geocoded once, cached in `data\.weather_location.json`) or `WEATHER_LAT` / `WEATHER_LON` in `.env`; unset = the source is skipped with a WARNING and the card shows `Weather: no data`. Pain index = the largest pressure change over any 12 h window (and any 24 h window) from 12 h before to 24 h after the wake anchor (08:30, or the run time when run later today): `pain_level` NONE / LOW (>= 1.5 hPa / 12 h) / MODERATE (>= 3 hPa / 12 h or >= 5 hPa / 24 h) / HIGH (>= 6 hPa / 12 h or >= 10 hPa / 24 h), `pain_index` 0-10. The tier change is **record-only by default** (`WEATHER_PAIN_DOWNGRADE_ENABLED = False`, until ~2026-11-13, so 2-3 weeks of `pain_level` vs `bb_wake` can be compared in `history.csv` first): HIGH adds a "record-only, no tier change" reason and never moves the tier; MODERATE adds a "plan for a pain day" reason only; LOW is card-only. With `WEATHER_PAIN_DOWNGRADE_ENABLED = True`, `pain_level` at/above `WEATHER_PAIN_DOWNGRADE_LEVEL` (HIGH; `MODERATE` to be stricter) joins the one-tier downgrade OR. A misspelt level logs one warning and disables the downgrade. Payload / mail JSON gain a `weather` object (pressure, worst 12 h / 24 h change with its window, pain index/level, temp, humidity, precip chance, condition, location); `history.csv` gains `pressure_hpa`, `pressure_d12_hpa`, `pain_level` for later pain-vs-pressure review; the raw response is kept in `data\raw\weather_<date>.json`. `python garmin_capacity.py --weather` prints today's object; `--no-weather` skips the fetch; `--mock weather-low|weather-moderate|weather-high|weather-high-24h|weather-none` exercise the rule.

**Record-only review fields (2026-10-23):** nothing here changes the tier, the bedtime or the deep-work blocks; every piece is fail-soft (a failure logs a WARNING and leaves the field null, the mail / card / calendar writer are never blocked). *Sleep timing:* `metrics.sleep_onset` / `wake_time` / `sleep_midpoint` (ISO local) with `timing_source` `garmin` (dailySleepDTO `sleepStart/EndTimestampLocal`) -> `sleepiq` (`bed_entry` / `bed_exit`) -> null; card line `Slept 1:05 AM → 10:20 AM (bed)` (`(watch)` when Garmin). *Alcohol:* `/drinks N [M/D]` on the bot (N 0-10 in halves; before 2 PM = last night, from 2 PM = tonight, a date overrides) appends `night_date,drinks,logged_at,source=telegram` to `data\alcohol.csv`; re-logging a night appends again and the LAST row wins. The morning run puts last night's value in `metrics.alcohol_drinks` — **null when nothing was logged, never 0** — card line `Alcohol last night: 2` or `Alcohol last night: not logged — /drinks N`. `history.csv` gains the appended columns `sleep_onset, wake_time, sleep_midpoint, timing_source, alcohol_drinks` (existing columns untouched, older rows blank). **Note on `bedtime_target` in `history.csv`:** it is the script's fixed-wake anchor (08:30 wake minus 8 h 15 min, pulled earlier by tier / sleep debt) and is NOT shift-aware; the shift-aware targets are the calendar's 🛏 / ☀️ events, which the review reads. *Backfill:* `python backfill_sleep_history.py [--days 365] [--end YYYY-MM-DD] [--dry-run]` writes `data\history_backfill.csv` (date, sleep_onset, wake_time, sleep_midpoint, sleep_min, sleep_score, bb_wake, bb_charged_overnight, resting_hr, hrv_last_night, hrv_status, source=garmin_backfill) for the last year: raw cache first, then Garmin at <= 1 request/s, one row appended per day so it resumes where it stopped; a day without a sleep record is written blank (watch off) and counted as missing. It never touches `history.csv`. Tests: `python -m unittest test_drinks -v`.

**Overnight fluid loss (2026-10-25, display only):** Darren weighs on the Garmin Index scale after the last pee at bedtime and after the first pee in the morning. The pull adds `get_weigh_ins(yesterday, today)` as `raw["weigh_ins_range"]` (the old `weigh_ins` / `body_composition` keys are unchanged for HealthAI). Garmin returns weight in **grams** (`93599.0` = 206.4 lb) with `timestampGMT` = epoch ms UTC, converted to `OVERNIGHT_TZ` (America/New_York); the record's `date` field is a wall clock in another zone and is ignored. pm = the LAST weigh-in from 19:00 yesterday to 04:00 today, am = the FIRST from 04:00 to 12:00 today. `payload.overnight` = `{pm_weight_lb, pm_time, am_weight_lb, am_time, delta_lb (pm − am, positive = lost), delta_ml_est (delta_lb × 453.6, nearest 10), hours_between, missing "pm" | "am" | null}`; with one side missing the object is kept and `missing` says which; both missing or a scale error (WARNING in `data\task.log`) → `null`. Card line `Overnight: 245.2 → 242.8 lb = −2.4 lb (~1090 mL, 8.6 h)`, `Overnight: missing bedtime weigh-in (...)`, `Overnight: missing morning weigh-in (...)` or `Overnight: no weigh-ins (scale)`. Garmin's API returns only weigh-ins assigned to this profile, so a reading left unassigned on the shared scale (or claimed by Tricia's profile) is invisible here. No tier, bedtime or deep-work effect; not in `history.csv` yet. *12:15 update pass:* `Capacity_Morning` has a second daily trigger at 12:15 (same command line). A plain run on a day that is already published (`data\<date>.json` with a tier) fetches only the weigh-in range (one Garmin request), recomputes `payload.overnight` and, **only if it changed**, rewrites the data files and re-sends the Telegram card and the `[CAPACITY]` mail (same subject; the JSON carries `as_of` and `overnight_updated_at`). Unchanged → nothing written, nothing sent (INFO line in `task.log`). `--refresh` still forces the full re-pull + re-publish; `--dry-run` on the update pass prints only. Card line 1 shows the Garmin pull time, `🔴 CAPACITY RED — 2026-10-25 (as of 09:00)` (`payload.as_of`); a weigh-in picked up later ends the Overnight line with `· as of 12:15` (`overnight.fetched_at`). `--mock overnight|overnight-pm-only|overnight-am-only|overnight-none|overnight-late-am` exercise the block; `python -m unittest test_overnight -v` covers the 09:00 → 12:15 → repeat sequence (filled once, re-sent once, identical afterwards).

**Nightly check-in (2026-10-25, display only):** the Health Consultant bot asks four button questions at wind-down (`CHECKIN_TIME` in `.env`, default `23:15`; `/checkin` starts it any time): (1) drinks today None / 1 / 2 / 3 / 4+ (the question shows what `/drinks` already logged; the answer sets the day's total and is written to `data\alcohol.csv` with source `checkin`, so the two agree); (2) NEW open wounds No / Yes → how many 1 / 2 / 3+ → where, multi-select Face/mouth, Scalp, Hands/arms, Legs/feet, Torso/back, Other → Done; (3) older wounds None open / Healing / Getting worse; (4) exercise No / Yes → type multi-select Strength training, Treadmill, Walking outside, Elliptical, Biking, Hiking → minutes <15 / 15-30 / 30-60 / 60+. One nudge 45 min after the last prompt; still unanswered 45 min later → the row is logged with status `skipped` (answers given so far are kept). The day follows the `/drinks` rule (before 14:00 = yesterday, from 14:00 = today). A missed 23:15 start is made up until 05:15 if the bot was down. Rows go to `data\checkin.csv` (`day, status, drinks, new_wounds, new_wound_count, new_wound_sites, older_wounds, exercise, exercise_types, exercise_minutes, started_at, finished_at, trigger, source`; lists `;`-joined; the LAST row per day wins; unanswered = blank, never 0 / no). The in-flight check-in survives a bot restart via `data\checkin_state.json`. Backfill / manual rows: `python capacity_bot.py --checkin-log 2026-10-24 new_wounds=yes new_wound_count=unknown new_wound_sites=Scalp exercise=no`. Morning run: `payload.checkin` (previous evening's row, lists as arrays, null when none) and the card line `Check-in Sat 10/25: drinks 2 · new wounds 1 (Scalp) · older: healing · exercise Walking outside 30-60 min` (`?` for anything unanswered). No tier / bedtime effect. `--mock checkin|checkin-skipped|checkin-none`; tests `python -m unittest test_checkin -v`.

**Secrets:** Windows user environment variables win, then `.env` here. There is no CrystalBull fallback any more (removed 2026-10-18): Telegram and Gmail come only from this folder's `.env`. `GARMIN_EMAIL` / `GARMIN_PASSWORD` live only in the Windows user environment (`setx`, single-quote the password); leave them blank in `.env`. They are used by `--setup` only.

**Auth (shared with HealthAI's `garmin_fetch.py`):** one token store, `%USERPROFILE%\.garminconnect` (`garminconnect` 0.3.x, override with `GARMINTOKENS`). Scheduled runs are token-only: they never attempt a credential login, so a stale password can't trip Garmin's 429 throttle. If the token is missing or rejected the run fails and says to run `--setup`, which is the only path that logs in (email, password, MFA) and writes the token. This is an unofficial API, so if Garmin changes its login, run `pip install --upgrade garminconnect` first.

**One fetch per day:** `data\raw\<date>.json` carries `_meta.fetched_at`. A run less than 20 h after that reuses the file instead of calling Garmin (`--refresh` overrides). `garmin_fetch.py` (HealthAI) reads the same raw file first, so the two projects never fetch twice. The raw pull also includes stress, resting HR, body composition, weigh-ins (`weigh_ins` for today, `weigh_ins_range` for yesterday..today) and hydration for HealthAI.

**Debug:** `python garmin_capacity.py --dry-run` · `--mock` · `--refresh` · `--date YYYY-MM-DD` · `--now --dry-run`
